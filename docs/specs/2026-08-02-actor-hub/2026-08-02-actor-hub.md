## 1. The architecture

> **Features are PLUGINS. The actor is the HUB.**

The hub holds a being's identity and what is **intrinsic** to it, tracks **which plugins are attached**, and
**folds** their contributions. **It knows nothing about what any contribution means.**

**Actor hub is feature #1 of roughly a thousand.** Its job is to make adding feature #2 cheap — **not to
pre-empt it.**

## 2. The scope test

> **身外之物** — *a thing outside the body.*
> **Strip the actor naked and move them to another world. What travels with them?**

| **travels — INTRINSIC, the hub's** | **stays behind — EXTERNAL, a plugin's** |
|---|---|
| body · cultivation base · soul · lifespan | money · treasures · items · equipment |
| wounds · statuses · pools | sect rank · titles · reputation |
| memories · comprehension | relationships · position in the world |

> **If a datum would not travel with a being stripped naked into another world, it does not belong in the
> actor — however convenient it is to put it there.**

**The test applies to QUANTITIES AND STATE.** It does **not** rank **identity** (which is what the test is
about, so asking is circular) or **record lifecycle** (a property of the row, not of the being). Stated as
universal it evicts items 1 and 3 below, which is how the bound was found.

**What it does not settle:** a datum **intrinsic in form and external in referent** — a tier index selecting
a row of the *origin* ruleset's ladder, a lifespan denominated in the *origin* world's time. **The declaring
plugin says which.**

## 3. What the hub holds — five things

```
1  IDENTITY             EntityId                      — shipped: sim-core/src/types.rs:17
2  INTRINSIC QUANTITIES [i32; MAX_DECLARED_QUANTITIES] — 128 B; the domain says how to read a slot
3  EXISTENCE            GoneState                     — shipped: dp-kernel/src/entity_status.rs:28
4  ATTACHMENT           PluginSet — a u32 bitmask over plugin ordinals
5  THE FOLD             aggregate contributions, and know NOTHING about what they mean
```

### 3.1 Identity

`EntityId(u64)`, shipped, with 36 consuming sites. **The shipped engine has never known what an "actor" is;
it holds things by `EntityId`.** A faction, a world, a place and a person are all entities. **Which kinds
exist is the actor and social features' vocabulary.**

**`EntityId` is documented as *"identity within a reality"*.** The platform's lifecycle keyspace is a
different one — `EntityRef { uuid, aggregate_type, reality_id }` — with **zero conversion sites**. **The
bridge is a seam** (`S-9`), not feature #1's work.

### 3.2 Intrinsic quantities

One `i32` per ordinal; **how to read a slot is declared, not stored**. What may occupy a slot is decided by
§2's test.

A quantity is present because **a plugin that declares it is attached** — §3.4.

### 3.3 Existence

**`GoneState = Active | Severed | Archived | Dropped | UserErased`**, already shipped with a precedence
lattice, a Go mirror, and `is_live()` / `is_terminal()`.

> **It answers *"is this row reachable?"* — platform existence. Fiction existence, alive or dead, is a
> STATUS and is not here.** Two beings can both be `Active` while one is a corpse.

**Honest measurement:** the type is fully built and **consumed by nothing yet** — 27 of its 51 grep lines are
its own tests, and the 3 outside the defining file are comments. That does not change the decision; it means
adopting it is free rather than entrenched.

**Not here:** the materialisation tier and residency — zero code occurrences, and by §2 they are the
substrate's. ***Where* a being's state lives is not *what* a being is.**

### 3.4 Attachment

A **`u32` bitmask over plugin ordinals**, assigned once and **never reused** — the law the quantity ordinals
already live under, because a renumbering silently redefines every stored value. `u32` matches
`MAX_DECLARED_QUANTITIES` so the two ceilings move together; **raising it later moves no existing digest,
lowering it is impossible.**

**`granted` is not a field.** Quantity `q` is present **exactly when the plugin that declares `q` is
attached** — a village has no hp because combat is not attached; a stone has no qi because cultivation is
not. **One fact, nothing to keep in step.**

### 3.4b Initial values — the hub's whole obligation

> **Every quantity of every attached plugin begins at the initial value that plugin's own declaration
> supplies. A quantity of an unattached plugin is ABSENT, not zero.**

`ResourceDecl.base` is already documented as *"the value an actor starts at"*. **The hub reads it; it does
not author it.**

**NOT a hub concern:** where an entity comes into existence · what kind of thing it is · what template it
draws from · who attaches its plugins. **Each belongs to a feature, and each of those features is unbuilt.**

### 3.5 The fold

Aggregate contributions from attached plugins. **The arithmetic is the substrate's.** The hub's contribution
is that it folds **without knowing what any contribution means**.

## 4. The contribution seam — the whole plugin contract

```
ModifierRow    { target: QuantityOrdinal, op, source: PluginOrdinal, fold_layer }
DerivationRow  { target: QuantityOrdinal, source_quantity: QuantityOrdinal, op,
                 factor_milli, divisor, bound, source: PluginOrdinal, fold_layer }
```

> **AMENDED 2026-08-02, at the build, with the reason.** The sealed version read
> `ModifierRow { …, op, value, … }` and `DerivationRow { target, source, op, factor_milli, bound }`.
> Three corrections, each forced by implementing it:
>
> * **`op` carries its value.** `D-253` chose the shipped `ModifierOp { Flat(i32), Percent(i32) }`,
>   which is one field, not two. A `DerivationRow`'s amount is *computed*, so it stores the
>   channel alone (`OpKind`) and the op is rebuilt once the amount is known.
> * **`divisor`** — `U-6`. `factor_milli` alone cannot express the shipped move-range derivation:
>   `10 000 / 3 = 3 333`, while the nearest per-mille factor gives **3 330**.
> * **`source` is a `PluginOrdinal` on BOTH rows, and the derivation's quantity is
>   `source_quantity`.** The sealed text used `source` for two different things one line apart —
>   the submitting plugin on a `ModifierRow`, the quantity read on a `DerivationRow`. One name for
>   one concept; the second got a name of its own. Both rows also carry `fold_layer`, without which
>   the layer ordering has nothing to order by.
>
> **The contract was amended rather than the code bent to fit it**, because a reader following
> *"the only specification"* would otherwise read `source` as a quantity and be handed a plugin.

| rule | why |
|---|---|
| **A contribution is DATA, never executable logic.** | The whole decoupling. A plugin cannot run inside the fold, and the fold cannot run inside a plugin |
| **A row addresses an ORDINAL, never a name.** | The address is mechanism; the name is the author's |
| **A condition is a declared threshold**, never a predicate grammar | a grammar is code wearing a data costume |
| **The hub never inspects `fold_layer` semantically.** | It orders by it and nothing else. **If the hub ever needs to know what a layer MEANS, a plugin's vocabulary has leaked in** |
| **A `DerivationRow` CONTRIBUTES; it never SETS.** | The shipped `derive_move_range` ends in `self.set(…)`, overwriting a value six layers just resolved — so an Equipment `Flat(+2)` on `MoveRange` is accepted and silently discarded today (`S-4`). SET would adopt that defect as a design |

**`fold_layer`, not `layer`** — `ruleset-loader/src/layer.rs:22` already ships an unrelated `Layer` whose
`ALL` is documented at `:44` as *"Ascending priority — the fold order."* **One name, two concepts, avoided.**

**The hub guarantees a stable total order by fold-layer ordinal.** Which fold layers exist, and what they are
called, is **declared** — so a plugin adds one without the engine learning its name.

**The clamp channel is NOT a fold layer.** In shipped code these are two channels: a `Lex` modifier is folded
by the same loop as the other five, while the inescapable clamp arrives through **a different parameter**. A
`u8` ordinal cannot express *"and also a clamp channel"*. **That seam is UNWRITTEN** (`U-2`).

**Its non-vacuous gate:** *every `fold_layer` value present in a submitted row names a DECLARED fold layer* —
which reds when a plugin ships a row for a layer it forgot to declare (`U-7`). *(An earlier draft proposed
"every declared layer is reachable by the resolver", which cannot fail once the resolver iterates the
declaration list.)*

## 5. Cost

A fold that asks three plugins is slower than one reading three local fields.

> **Attachment does not mean remote.** A plugin attached to a **resident** actor is resident too. What is
> forbidden is a plugin's data living inside the actor's **struct** — not inside the same memory tier.
> **Only the first creates a second SSOT.**

## 6. The acceptance test

> **Adding a feature must touch ZERO files in actor core.**

Under this frame it is checkable, because a plugin that cannot add a field has nothing to touch.

**The honest bound: it holds UP TO THE DECLARED WIDTHS.** The 33rd plugin, and the plugin whose quantities
exceed 32, **do** touch actor core — and that is a **version bump**, visible and costed, not a silent
failure.
