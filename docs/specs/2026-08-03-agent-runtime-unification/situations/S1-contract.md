# S1 — P2 declaration contract: situation coverage interrogation

**Module:** P2, clauses C-1 … C-12 (`ARCHITECTURE.md` §4 + §0.5).
**Question 1:** what concrete situation does each clause exist to solve, and does that situation
actually occur in this repo?
**Question 2 (the important half):** what situations *certainly occur* that the contract has **no
defined answer for**?

**Method — no theorizing.** Every row below is grounded in one of:
- the live tool-call history: `docker exec infra-postgres-1 psql -U loreweave -d loreweave_chat`,
  `chat_messages.tool_calls` jsonb — **7,447 calls · 3,437 ok · 4,010 failed · 222 distinct error strings**;
- the MCP tool definitions (`@mcp_server.tool` + `require_meta` in Python, `NewToolMeta`/`WithAsync` in Go);
- `docs/standards/mcp-tool-io.md`;
- incident write-ups in `docs/eval/`.

## 0 · Headline

**The contract's twelve clauses cover the failure path well and the *success* path barely at all.**
Nine of the twelve clauses govern what happens when a call is rejected. But the largest uncovered
classes in the real data are all **`ok=true`**:

| the model was told | count | contract's answer |
|---|---|---|
| "success" + a payload that is actually a refusal | **358** | none |
| "success" + an empty result that may mean *not found*, *not permitted*, or *not indexed* | **400** | none |
| "success" + nothing changed (idempotent re-hit) | **261** | C-8 half-covers (it forbids reporting success; it does not say what to report *instead*) |
| "success" + a batch where some items failed | **59** | none |
| "success" + one of N equally-good matches, silently picked | **14** | none |

C-5 forbids **argument** substitution. Nothing forbids **result** substitution, and that is where the
`ok=true` classes live. This is exactly the class §4.1 of `DESIGN-HYPOTHESIS.md` named — *"this repo
counts only loud failures"* — restated as a contract gap rather than a metrics gap.

## 4 · The shape of the gap, in one sentence

> **C-1 … C-12 define how a declaration FAILS. They do not define what it means when it SUCCEEDS.**

Every missing clause above is a species of the same omission: `ok=true` is currently an
**untyped** signal that can mean *done*, *done to some of it*, *done to something else*, *refused*,
*deferred*, *degraded*, or *unknown* — and the model must guess which from prose. That is the same
defect the PO named for failures (*"the model cannot tell, so it loops"*), on the other channel, and
it is worse, because a wrong `ok=true` does not make the model loop — **it makes the model proceed on
a false premise and produce wrong work** (`ARCHITECTURE.md` §0.5, shape 1).

**All fifteen proposed clauses pass the §0.3 Ceiling Test as enablers.** Not one narrows the action
space; every one adds a field, a name, or a reachable partner declaration. Two (C-17, C-14) actively
*repair* an existing ceiling — an invisible, unappealable narrowing that the model cannot know about.
