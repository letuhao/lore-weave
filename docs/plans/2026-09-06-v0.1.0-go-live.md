# Implementation Plan: v0.1.0 go-live — task breakdown + checklist

Branch: release/v0.1.0
Created: 2026-09-06

## Original Request
approve this release list, we need task breakdown and make go live checklist plan

## Settings
- Testing: yes — regression testing against a scratch stack IS this plan's core content, not an add-on
- Logging: standard — most tasks are verification/process steps against existing services, not new instrumented code; where a bug fix touches code, follow that file's existing log-level convention (this repo already logs heavily at INFO/DEBUG throughout)
- Docs: yes, mandatory — Phase 5 ends in a real reviewed runbook + a finalized `CHANGELOG.md [0.1.0]` section, not optional

## Branch discipline (from the user directly — binding for every phase below)
**A bug fix must never exist ONLY on `release/v0.1.0`.** Every fix found during go-live testing is
fixed and merged to `main` (fix-on-main-then-merge-into-release, or fix-on-release-then-immediately
merge-to-main — either order, same outcome required), so `release/v0.1.0` never drifts into a fork
holding un-merged fixes. The final `v0.1.0` tag is cut from `main` once `release/v0.1.0` is clean and
fully merged back — not from the release branch directly.

Milestone: "none"
Rationale: No `.ai-factory/ROADMAP.md` exists in this repo; the authoritative planning corpus is
`docs/plans/` per this repo's own `aif-plan` skill-context override.

### Phase 3 — Regression, blind-spot discovery & visual review (depends on Phase 2)
- [ ] **T7** — Identify what automated regression coverage already exists and is scoped to the 33
  in-scope services (this repo has a large existing test corpus per this session's CI work — the
  actual command(s) need confirming, not assuming: likely a mix of Go/Python/frontend unit+
  integration suites and Playwright e2e). Run the FULL relevant set against the scratch stack from

- [ ] **T8** — Run `/human-sim` (`newcomer` and `frequent` personas) against the scratch stack's live
  UI to find blind spots automated tests structurally cannot: empty states, dead ends, unexplained
  vocabulary, anything that only shows up walking a real journey end to end. A blind spot found here
  gets FIXED and re-verified in Phase 4 — logging it and moving on does not close it.
- [ ] **T9** — Live GUI run with computer-vision review, for the class of gap neither code review nor
  a passing test can see: DOM/testid correctness says nothing about whether the pixels are actually
  right. Using Playwright/`chrome-devtools` tooling, drive the same key journeys T8 covers PLUS
  purely-visual surfaces (light/dark theme, responsive breakpoints, empty/loading/error states),
  capturing a real screenshot at each step. The acting agent then looks at every screenshot directly
  (this session's own multimodal vision — reading a rendered image is a normal `Read` call, not a
  separate paid vision-API pipeline) hunting specifically for: misaligned/overlapping/truncated text,
  broken images, unreadable contrast, inconsistent theming, layout that breaks at a breakpoint,
  content clipped or rendering off-screen. Each finding needs the screenshot path plus a one-line
  expected-vs-actual statement — same bar as a real bug report, not an impression.
- [ ] **T10** — For every finding from T7–T9, open one line in a findings log (which findings are
  real regressions vs. pre-existing/known/out-of-scope) — mirroring this session's own "attribute

This session's `/goal-prompt-testing` command derives its `/goal` condition from the block below
rather than the whole plan — Phase 1 (changelog draft) and Phases 5–6 (checklist, merge, tag) are
real work but are not TESTING work, and pooling them into one goal would dilute the discipline this
block exists to state.

```goal-prompt
goal: every blind spot /human-sim and a real computer-vision GUI review can find in v0.1.0's novel-writing-platform scope is found, reproduced, fixed, and re-verified -- and every fix has landed on main, never stranded on release/v0.1.0
excluded: [T0.1, T0.2, T0.3, T0.4, T0.5, T0.6, T1, T2, T13, T14, T15, T16, T17]
rules: |
  1 A blind spot without a reproduction is an impression, not a finding. Reproduce it before it counts.
  2 Found is not done. A human-sim or visual finding that is not FIXED and RE-VERIFIED stays open.
  3 A screenshot with no stated expected-vs-actual is not a code-review-uncoverable gap, it is a vibe. Name what should have rendered and what did.
  4 Visual review means LOOKING at the real rendered screenshot yourself. Inferring correctness from a passing testid or DOM snapshot is exactly the blind spot this technique exists to catch.
  5 A fix that changes code and is not re-screenshotted is not verified to look right. A green diff is not a green eye.
  6 Every fix lands on main, never stranded on release/v0.1.0 -- the plan's own branch rule, restated because it is the one rule a testing loop is most tempted to defer "until later".
  7 A "no issues found" verdict must name what was actually looked at (pages, personas, breakpoints). An unscoped clean bill of health is the same defect as an unscoped test pass.
  8 Do NOT fan out subagents per screenshot or per page. Group by user journey, or stay solo.
  9 Record a near-miss (looked wrong at first glance, then wasn't) as it happens. Zero near-misses logged means the screen was not really looked at.
discipline: |
  No "looks fine" without the screenshot it is based on attached to the claim.
  No prose-only cycles. Updating the findings log is a STEP of a cycle, never a whole cycle.
  Commit every fix-and-reverify cycle. Keep the repo's gates green.
stop: |
  a finding would change what is IN v0.1.0's shipped scope -- that is a product decision, not a bug fix
  a finding can only be verified by a paid or cloud model call -- the default is the acting agent's own vision reading local screenshots at zero extra cost; a real separate paid vision pipeline needs the same explicit-yes-and-call-count rule this session has used everywhere else
```
