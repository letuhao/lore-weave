## The danger this plan is built around

Twenty-two of the 51 are already known to be the harness, not the product. That makes this plan's
work look cheap and makes its failure mode invisible: **the fastest way to close every row is to
edit each test until it passes, and that would destroy the suite's value while producing a
beautiful green number.** A stale selector "fixed" by pointing at whatever element happens to be
nearby is not a repair — it is a test that no longer asserts anything, and it would tell the PO the
product works when nobody checked.

So the mechanism is NV-6, applied to the REPAIRED test rather than to a new one: **break the
product behaviour the test claims to guard, and watch the repaired test go red for the right
reason.** A repaired test that cannot be made to fail was not repaired; it was removed.

## Why the harness rows come first, and it is not because they are easy

**A harness defect that aborts a test conceals whatever that test was going to find.** All nine A1
tests die at `page.waitForURL('**/books')` before their first real assertion, so nine journeys
through publish, translation, assembly and the wiki dock have never once been evaluated on this
build. They are not nine known-good tests with a bad wrapper; they are nine unanswered questions
wearing a harness failure as a mask. The same is true of A3 and A4.

Clearing Lane A does not make the number better — **it is expected to make the number worse**, by
letting tests reach assertions they have not reached in this run at all. If Lane A closes and the
failure count does not move, that is itself a finding worth a second look.

### Cycle 5 — the suite could write into the developer's own database (A5, A7)

**Investigated:** `specs/frontend-tools-liveness.spec.ts:17,21,63`; `helpers/db.ts:7`;
`infra/docker-compose.yml` (header: base gateway is 3123) and `docker-compose.isolated.yml`

**Issues:** none filed — every defect here is this repo's own harness and has no user surface.
It is written up at length because the hazard is the kind that is invisible until it has already

**Fix:** A5's premise was wrong. The session is not "never seeded" — the spec was **welded to the
BASE stack** in four places: the gateway defaulted to `localhost:3123`, `helpers/db.ts` shelled out

`claude-test` account. So a run pointed at the ISOLATED frontend drove the UI on `lw-iso` while
reading **and writing** `infra` — and `seedPriorExtractionJob()` INSERTs. That is a cross-stack
write into a database nobody treats as disposable, and it is silent: the specs then pass or fail
for reasons belonging to the other stack.

New `helpers/stack.ts` derives the Postgres container and the gateway from the BROWSER TARGET, so
the safe thing is the default rather than something to remember; an explicit env still wins. The
model is read from the registry and the user id from the token's own `sub`, so the spec no longer
requires one particular account to exist.

**Proof:**

```

AFTER -- by effect, which stack actually received the write:
  ISO  chat_sessions WHERE title='fe-tools liveness' -> 1

```

`0` on the base stack is the load-bearing half: the writes now land where they belong.
Four specs share `helpers/db.ts` (`composition-telemetry`, `composition-flywheel`,
`composition-correction-gate`, `frontend-tools-liveness`), so **C1 and D11 were both asserting

## What this plan will NOT do

- **It will not edit a test to match whatever the product now does.** A selector is repaired only
  when the new target is the control the test MEANT, and the bite proves it.

- **It will not retry a test until it passes.** "Flaky" is not a verdict.
- **It will not run against anything but loopback** — these journeys register accounts and seed books.
- **It will not tag, build or publish anything.**
