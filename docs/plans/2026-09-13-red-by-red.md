## The danger this plan is built around

Twenty-two of the 51 are already known to be the harness, not the product. That makes this plan's
work look cheap and makes its failure mode invisible: **the fastest way to close every row is to
edit each test until it passes, and that would destroy the suite's value while producing a
beautiful green number.** A stale selector "fixed" by pointing at whatever element happens to be
nearby is not a repair — it is a test that no longer asserts anything, and it would tell the PO the
product works when nobody checked.

So the mechanism is NV-6, applied to the REPAIRED test rather than to a new one: **break the
product behaviour the test claims to guard, and watch the repaired test go red for the right
reason.** A repaired test that cannot be made to fail was not repaired; it was removed.

## Why the harness rows come first, and it is not because they are easy

**A harness defect that aborts a test conceals whatever that test was going to find.** All nine A1
tests die at `page.waitForURL('**/books')` before their first real assertion, so nine journeys
through publish, translation, assembly and the wiki dock have never once been evaluated on this
build. They are not nine known-good tests with a bad wrapper; they are nine unanswered questions
wearing a harness failure as a mask. The same is true of A3 and A4.

Clearing Lane A does not make the number better — **it is expected to make the number worse**, by
letting tests reach assertions they have not reached in this run at all. If Lane A closes and the
failure count does not move, that is itself a finding worth a second look.

## Cycles

### Cycle 1 — nine journeys were masked by a throttle, not a redirect (A1)

**Investigated:** the nine `waitForURL` failures in the 2026-09-13 full run; their Allure
`statusDetails`; `helpers/auth.ts:21`; `services/auth-service/internal/api/server.go:153`;
`internal/ratelimit/limiter.go:84-96`; `internal/config/config.go:94,124`; and the live `lw-iso`
stack by driving real logins at it.

**Issues:** #261 — the throttle is keyed per IP, so everyone behind one NAT shares 60 logins a
minute. Two further findings are this repo's own and carry no user surface, so they are recorded
here rather than filed: **this plan's A1 premise was wrong** (it named the `/onboarding` redirect;
two traces log `navigated to ".../login"`, which a redirect to onboarding cannot produce), and **a
401 I reported mid-investigation was my own error** — I drove the probe with the suite's DEFAULT
account while the run used the seeded `iso-evidence@` one.

**Fix:** `RATE_LIMIT_MAX_REQUESTS` / `RATE_LIMIT_WINDOW_SECONDS` are passed through in
`infra/docker-compose.yml` **with the production values as their defaults**, and `infra/iso.sh`
raises the max to 2000 for the throwaway `lw-iso` project only. No test was edited and the
product's guard was not weakened; an explicit caller value still wins, so the limiter stays
testable.

**Proof:**

```
BITE (RATE_LIMIT_MAX_REQUESTS=5)          RESTORED (iso default)
  req 1 -> 200   req 5 -> 200               100 logins -> 200=100  429=0
  req 2 -> 200   req 6 -> 429               RATE_LIMIT_MAX_REQUESTS=2000
  req 3 -> 200   req 7 -> 429
  req 4 -> 200   req 8 -> 429             base stack, env unset:
                                            RATE_LIMIT_MAX_REQUESTS: "60"

causal, not correlational -- limiter saturated, then the same test re-run:
  Error: API login iso-evidence@loreweave.dev failed: 429 {"code":"AUTH_RATE_LIMITED"}

  that test ALONE ............................ 1 passed (13.5s)

  only the full 76-spec load reds them
```

**AC impact:** AC-1 — nine failures move from "environment, stale selector" to **environment,
throttle saturation**, a different owner and a different fix. AC-2 is not applicable: no test was
repaired, so there is no repaired test to re-bite, and the bite was taken against the mechanism
instead. AC-3 holds — no test's claim was touched. AC-5 stays open: that the nine pass under FULL
load is not yet observed and is Z1's job. Claiming it here would be the untested assumption this
plan exists to stop.

**Still owed:** the `/onboarding` vs `/books` defect in `helpers/auth.ts:21` is real for a FRESH
account and simply was not what broke these nine — they use the seeded account, which is past
onboarding. It stays open as its own row rather than being folded into this one.

## What this plan will NOT do

- **It will not edit a test to match whatever the product now does.** A selector is repaired only
  when the new target is the control the test MEANT, and the bite proves it.
- **It will not delete, `skip`, or `fixme` a failing test to clear a row.**
- **It will not retry a test until it passes.** "Flaky" is not a verdict.
- **It will not run against anything but loopback** — these journeys register accounts and seed books.
- **It will not tag, build or publish anything.**
