## The danger this plan is built around

Twenty-two of the 51 are already known to be the harness, not the product. That makes this plan's
work look cheap and makes its failure mode invisible: **the fastest way to close every row is to
edit each test until it passes, and that would destroy the suite's value while producing a
beautiful green number.** A stale selector "fixed" by pointing at whatever element happens to be
nearby is not a repair — it is a test that no longer asserts anything, and it would tell the PO the
product works when nobody checked.

So the mechanism is NV-6, applied to the REPAIRED test rather than to a new one: **break the
product behaviour the test claims to guard, and watch the repaired test go red for the right
reason.** A repaired test that cannot be made to fail was not repaired; it was removed.

## Why the harness rows come first, and it is not because they are easy

**A harness defect that aborts a test conceals whatever that test was going to find.** All nine A1
tests die at `page.waitForURL('**/books')` before their first real assertion, so nine journeys
through publish, translation, assembly and the wiki dock have never once been evaluated on this
build. They are not nine known-good tests with a bad wrapper; they are nine unanswered questions
wearing a harness failure as a mask. The same is true of A3 and A4.

Clearing Lane A does not make the number better — **it is expected to make the number worse**, by
letting tests reach assertions they have not reached in this run at all. If Lane A closes and the
failure count does not move, that is itself a finding worth a second look.
